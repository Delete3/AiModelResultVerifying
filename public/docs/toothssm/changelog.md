# AI排牙 API 更新內容

最新的一版在最上面。每次 API 更新都會在這裡加一節，並同步更新「API 串接文件」。

## 2026-11-02（傍晚）　生成牙根加快：預設模式全程快約三分之一

嘉義、台中兩台正式版都換了版（嘉義 17:03、台中 17:07 各重新啟動一次）。**API 和參數都沒有改**，只多一個欄位；結果會有很小的差異（見下）。

- **變快的是「生成牙根」這一步**：每顆牙要讓 AI 的牙齒形狀模型貼合牙冠三次。這次把貼合的運算改用顯示卡的 TF32 模式，並讓第二次貼合接著第一次的結果做、不再從頭開始（前兩次合計從 1000 步減為 400 步）。接虛擬牙根時統一三角形方向的做法也改快了（做出來的牙逐位元組相同）。
- **時間**（Case 1，`res=128`，27 顆，預設 `crown=fit`、`root=virtual`，含排牙）：

| | 換版前 | 換版後 |
|---|---|---|
| 嘉義 RTX 5090 | 128 秒 | 83 秒（分牙 18、生成牙根 31、接牙冠 24、排牙 9） |
| 台中 RTX 5080 | 185–187 秒 | 127 秒（分牙 33、生成牙根 58、接牙冠 25、排牙 10） |

- `seg=ssm` 的其他設定也經過同一個生成牙根步驟，應該也會變快，但沒有量；API 文件的速度表只更新了預設那一列。
- **結果的差異**：這種貼合對運算的細微差異很敏感，任何改動都會讓牙軸移動約 1°，所以用嘉義主機上技師以 CBCT 做出的真牙根判斷（12 位病人、340 顆牙）：虛擬牙根的牙軸和真牙根的夾角平均 12.85° → 12.87°，沒有變差。
- 矯正團隊的 8 個測試病例（同樣的牙冠）：牙軸移動中位數約 1°（p90 約 5°）；排牙後的旋轉差最多 0.1°、位移差最多 0.02 mm；ABO7 8 例都相同；`issues` 6 例相同，另 2 例各少一筆 `gen.generated_root`（Case 5 的 24、Case 6 的 26 這次接上了虛擬牙根）。
- **新欄位** `results.fast_roots`：這筆 job 是否用了加速的生成牙根（兩台現在都是 `true`）。`GET /info` 也有同名欄位。
- 換版前兩台都沒有 job 在跑，也沒有還沒取走的結果（嘉義最後一筆 15:38 已由呼叫端刪除；台中最後一筆是 14:06，已超過 2 小時保留時間），所以沒有清掉誰的結果。

## 2026-11-02　只分牙＋生成牙齒、不排牙的模式

**API 沒有改，兩台的服務也沒有重新啟動**：這個模式本來就有（建立 job 時帶 `until=generate`），這次把它寫成 API 文件裡獨立的一節，並在嘉義正式版實際跑過（台中是同一版程式）。

- 建立 job 時加 `until=generate`：做完分牙和生成整顆牙（含牙根、牙軸、`issues`）就是 `done`，不跑排牙模型。`crown`、`root` 等參數照常可用，預設一樣是 `crown=fit`、`root=virtual`。
- 回傳的整顆牙在 `results.teeth`，和完整流程裡排牙前的牙相同；`results.aligned` 是空列表，`results.align`、排牙矩陣、ABO 都沒有。整包 zip 約 25 MB（含排牙約 130 MB）。
- 之後要排牙，對同一個 job 送 `/run`、`step=align` 即可，不必重新上傳。用 `/run` 換參數重新生成而仍然不排牙時，要帶 `until=generate`，否則會接著排牙。
- 嘉義實測：Case 1（`res=128`、27 顆）120 秒（分牙 18 秒、生成 102 秒）。
- **更正**：之前文件寫 `root=none` 的 job「`results.abo.input` 照樣有」，這是錯的。ABO（排牙前與排牙後）都在排牙那一步算，沒有排牙的 job 兩項都是 null。

- 兩台各用一筆全口實際跑過：嘉義 Case 6（`res=128`、22 顆）114 秒，`issues` 和測試版相同；台中 Case 1（`res=128`、27 顆）187 秒（換版前 185 秒）。
- 換版時兩台都重新啟動過；那之前 2 小時內兩台都沒有 job，所以沒有清掉誰的結果。

## 2026-11-02　回報分牙與生成的問題：`issues`（測試版）

只改測試版端點；正式版沒有改變。只新增欄位，原有的欄位和格式都沒變。

**回報**：Case 6 的 AI 分牙有錯，46 長到 47（46 其實不在），25 和 26 都被標成 26，但服務沒有說。

**原因**：分牙程式依每塊的 AI 投票、沿牙弓順序決定號碼（可以跳號），但不看每塊有多大，也不會把一塊切成兩塊。25 和 26 黏成一塊時，就整塊標成 26。46 長到 47 這件事，服務原本只在生成後的 `results.exact_crown.lower.engulfed` 列出，沒有放進 `warnings`，也沒有代碼。

**新增**：

- job 狀態多一個 `issues` 列表。每一筆有固定代碼 `code`、等級 `level`（`error`／`warning`／`info`）、`stage`、`jaw`、相關牙位 `teeth`、中文說明 `message`，以及數字依據 `details`。代碼和欄位見 API 文件「問題回報」。
- 分牙的問題在分牙做完時就出現（job 還在生成牙根時就讀得到）；生成的問題在生成後加上。`start=generate` 用自己的牙冠時，生成前也會檢查分牙。
- 每筆 `error` 和 `warning` 也加進 `warnings`（`[代碼] 顎: 說明`），只讀 `warnings` 的程式不用改。
- 發現問題時 job 照常跑完；要怎麼顯示、要不要擋下，由呼叫端決定。

**新的分牙檢查**（只看分牙結果的幾何，兩顎合計不到 1 秒）：

- 一顆牙的寬度像兩顆牙（`seg.merged`）。
- 依牙寬和牙弓順序，號碼對不上，例如缺牙沒有跳號（`seg.number`）。
- 號碼順序和牙弓位置不一致（`seg.order`）。
- 相鄰兩顆的分界線越過牙冠咬合面（`seg.boundary_on_crown`）。
- 空隙裡的牙齦和牙冠一樣高，可能有牙沒分到（`seg.unlabelled_tooth`）。
- 另外還有分成好幾塊、碎片、缺牙空間等提醒。

**驗證**：用嘉義主機上 53 例技師分好、標了號碼的 CBCT 牙根萃取案例當標準答案。門檻只用 33 例訂，再拿沒看過的 20 例測：

| | 沒看過的 20 例 |
|---|---|
| AI 真的分錯或標錯的顎 | 19 顎（共 65 處錯） |
| `error` 標到的顎 | 15 顎（79%） |
| `error` 抓到的錯處 | 55 處（85%） |
| `error` 的誤報 | 0 |

- Case 6：兩個錯都以 `error` 回報（`seg.merged` 25／26、`seg.boundary_on_crown` 46／47）；生成後另有 `seg.engulfed` 46／47。
- 另外 7 個測試病例中，有兩筆請矯正團隊確認：Case 8 上顎 `seg.number` 的 `error`（標成 15 的那顆寬 12.1 mm，像臼齒；可能是 15 不在、後面的號碼整排錯一號），以及 Case 5 下顎 `seg.unlabelled_tooth` 的 `warning`（35 與 37 之間的牙齦和牙冠差不多高）。
- 抓不到的：寬度差不多的牙互相標錯（47／48、16／17、下顎門牙、上顎 12／13、14／15）、31 和 41 左右對調、牙弓最後那顆臼齒整顆沒分到。

## 2026-10-30（晚，修正）　鄰接面不再缺一塊（測試版）

只改測試版端點；正式版沒有改變。API 參數與回傳格式都沒變。

**回報**：Case 7（job 4a17223cb1e4）的 25、35、37、45、47，在近心或遠心與鄰牙接觸的地方向內缺了一塊。

**原因**：不是擬合，是決定在哪裡切掉牙根的那一步。分牙的牙冠邊緣在接觸點下方會往上爬到接觸點（掃描器看不到接觸點底下），我們原本用邊緣的形狀判斷哪一段是這種「凹口」、哪一段是牙齦線。臼齒、小臼齒的接觸面很寬：例如 47 的近心，凹口高 4–5 mm、寬約 60°，被當成牙齦線，切線就沿著它爬上去，把整片鄰接面切掉。`root=none` 看到的是缺一塊；`root=virtual` 的虛擬牙根從缺口長下去，看起來是一條向內的深溝。

**修正**：

- 牙冠邊緣離鄰牙 1.5 mm 以內的部分，一律當成爬向接觸點的凹口，切線在牙齦高度直接橫過去。
- 切線在任何角度都不會高於那個角度的牙冠邊緣最低點。下顎門牙排得擠時，牙齦處離鄰牙也不到 1.5 mm，這條規則保證不會因此切到口掃牙冠。

**結果**（8 個測試病例，res 192，排牙前；回報那筆 job 用它自己的資料重算，結果相近：`none` 46% → 80%、`virtual` 59% → 91%）：

| | 修正前 | 修正後 |
|---|---|---|
| 鄰接面保留率（8 個病例，每筆的平均） | `none` 46–78%、`virtual` 59–88% | `none` 71–89%、`virtual` 79–94% |
| Case 7（回報的那一筆） | `none` 46%、`virtual` 59% | `none` 80%、`virtual` 91% |
| 細長三角形、自交、鄰牙重疊、貼合口掃 | — | 不變；修整後口掃牙冠的 p99 有幾筆變好（Case 7：0.14 → 0.09 mm） |
| 接牙冠這一步的時間 | — | 不變（Case 7 經 API：`none` 20 秒、`virtual` 30 秒） |

「鄰接面保留率」：AI 牙齒上離鄰牙 1 mm 以內、又在口掃牙冠附近（2 mm 內）的區域，交付的牙齒還保留多少。不會到 100%，因為這個區域會延伸到牙齦線以下，那一段本來就切掉或換成虛擬牙根。

仍有的例外：Case 6（分牙把下顎 46 切錯）的 `virtual`，和上一版一樣。

**怎麼試**：同一個 job 重新送一次，或在 eztest「AI排牙」用「嘉義 5090 測試（牙冠貼合口掃）」重跑；不用改任何參數。

## 2026-10-30（晚）　AI 牙齒擬合口掃：不再有細長三角形（測試版）

只改測試版端點 `https://ezai2.inteware.com.tw/toothssm-fit`；正式版（嘉義、台中的 `/toothssm`）沒有改變。新增 `crown=fit`，並改為測試版的預設。

**為什麼改**：`root=none` 回傳的牙冠，鄰接面凹口是用一條三角形帶從凹口一側直接連到另一側（最寬約 6 mm），所以有很多細長三角形。以 10-30 下午測試的那一筆為例，補上的 5,359 個面裡 96% 最小角小於 10°、86% 有一邊超過 1 mm；口掃本身的面只有 0.3%，也沒有超過 1 mm 的。`root=virtual` 的短牙根和 `generated` 的接合帶也有同樣的問題。

**改了什麼**（`crown=fit`）：

- 從 AI 生成的整顆牙出發：先重新網格化成邊長約 0.2 mm 的均勻三角形，再把牙冠部分拉到口掃上（非剛性擬合）；鄰接面接觸點下方與牙根只求平順。
- 擬合之後才推開鄰牙，只動不在口掃上的部分；兩顆牙在緊接觸點互搶的那一小塊口掃面，也一起放開推。
- 依 `root`：`generated` 回整顆擬合後的牙（封閉、沒有縫線）；`none` 在平滑的牙齦線處切開，鄰接面切在牙齦高度、不再沿凹口爬到接觸點，切口不留細長三角形；`virtual` 從這個切口接矯正式短牙根，牙根也重新網格化。
- 要回到口掃原樣的牙冠，送 `crown=exact`。
- 狀態回應的 `results.exact_crown.{jaw}` 多 `crown`（`fit` 或 `exact`）與 `triangles`（面數、最小角小於 10° 的個數、一邊超過 1 mm 的個數）。

**8 個測試病例的結果**（res 192，排牙前的牙齒；「之前」是同一端點 10-30 下午的 `crown=exact`）：

| | 之前（`crown=exact`） | 現在（`crown=fit`） |
|---|---|---|
| 最小角小於 10° 的三角形 | `none` 1.0–4.9%、`virtual` 10–28%、`generated` 5.0–7.3% | 0.00–0.04% |
| 一邊超過 1 mm 的三角形（每筆） | `none` 1,859–4,720 個、`virtual` 5,163–9,304 個、`generated` 524–2,215 個 | 0 |
| 自我交叉的三角形（每筆） | `none` 116–713 對、`virtual` 348–3,539 對、`generated` 6,742–23,927 對 | 0–89 對 |
| 互相穿插的相鄰牙 | 0 | 0（兩筆各一對 0.001–0.002 mm³，屬數值誤差） |
| 修整後的口掃牙冠落在結果 0.05 mm 內 | 100% | 96.5–98.7% |
| 同上，0.01 mm 內 | 100% | 70–87% |
| 改接整顆牙的牙（`virtual`） | 1 顆 | 2 顆 |
| 接牙冠這一步的時間（Case 1，經 API） | `none` 14.1 秒、`virtual` 23.6 秒 | 21.0 秒、29.3 秒（每筆多 6–7 秒） |

例外：Case 6（分牙把下顎 46 切成一大片的那一筆）的 `virtual`，46 接不上虛擬牙根、改接整顆牙後被推開變形，這一筆有 907 個細長三角形、141 個長邊、1,703 對自交、和 47 重疊 1.1 mm³；同一筆的 `none`、`generated` 都正常，46 也會列在 `engulfed`。

**已知問題**：

- 牙冠不再是口掃原本的頂點，而是貼在口掃上的新網格。偏最多的是分牙邊緣最外一圈翻到牙齦上的口掃，擬合刻意不跟過去（0.05 mm 以外的點約九成在那裡）。
- 鄰接面接觸點下方、牙齦線到切口之間是 AI 生成的牙面，不是口掃。
- 牙冠貼口掃的精度比 `crown=exact` 低：0.01 mm 內從 100% 降到 70–87%（0.05 mm 內仍有 96.5–98.7%）。
- 自我交叉沒有完全歸零（每筆 0–89 對，和 AI 生成牙齒本身相當）。
- 根分叉剛好在牙齦線高度的牙（Case 6 的 26），切下來的牙冠開口裡會多一小片舌狀的面；仍只有一個開口邊緣，`virtual` 會改接整顆牙。
- 排牙之後的干涉，以及 `start=generate`（你們自己的牙冠）搭配這個模式，仍未測。

**怎麼試**：eztest「AI排牙」主機選「嘉義 5090 測試（牙冠貼合口掃）」，「牙冠」預設就是「AI 牙齒擬合口掃」，可切回「口掃牙冠原樣」比較；結果區會列出每顎的細長三角形數。API 送 `crown=fit`（測試版預設）或 `crown=exact`。

## 2026-10-30　矯正式虛擬牙根、只回牙冠＋牙軸（測試版）

只改測試版端點 `https://ezai2.inteware.com.tw/toothssm-fit`；正式版（嘉義、台中的 `/toothssm`）沒有改變。新增參數 `root`，決定口掃牙冠下面接什麼：

| `root` | 回傳什麼 | 排牙 |
|---|---|---|
| `virtual`（測試版新的預設） | 口掃牙冠＋矯正軟體演算法（ToothRootLoft）做的 3 mm 短牙根，方向取自 AI 生成牙齒的牙軸；封閉 | 有 |
| `generated` | 口掃牙冠＋AI 生成的牙根（就是 10-29 的測試版） | 有 |
| `none` | 只有口掃牙冠，在牙齦線處開口，讓你們自己縫合牙根；附每顆牙的牙軸 | 沒有：job 做到生成牙根那一步就結束 |

**為什麼改**：10-29 的流程是「AI 生成整顆牙 → 取牙根和口掃牙冠縫起來」，AI 生成的牙根形狀複雜，接合帶有大量自我交叉的三角形。改成直接用矯正軟體的短牙根演算法接在口掃牙冠下面，自我交叉少很多、也比較快；若你們想用自己的牙根演算法，就用 `root=none`。

**新的輸出**：

- `root=virtual`、`none` 多一個 `result/tooth_axes.json`（也放在狀態回應的 `results.axes`）：每顆牙的牙冠中心、牙軸（從牙根指向牙冠）、唇頰側方向、AI 生成牙根的根尖，以及一個 4×4 矩陣。格式見 API 文件的「牙軸」一節。
- `root=none` 的 `result/{jaw}/teeth/tooth_{FDI}.ply` 是開口的牙冠：分割邊界的鋸齒修掉、鄰接面窄而深的凹口先縫起來，每顆只剩一個平順的開口邊緣。
- 狀態回應多 `results.root`；`results.exact_crown.{jaw}.generated_root` 列出 `root=virtual` 時改接 AI 生成牙根的牙。

**8 個測試病例的結果**（res 192，排牙前的牙齒）：

| | `generated`（10-29 的測試版） | `virtual`（新的預設） |
|---|---|---|
| 口掃牙冠的點落在結果上（≤ 0.01 mm） | 95–98% | 同左（同一個牙冠） |
| 互相穿插的相鄰牙 | 0 對 | 0 對 |
| 自我交叉的三角形（每筆） | 6,700–24,000 對 | 348–3,539 對 |
| 改接 AI 生成牙根的牙 | — | 8 筆共 1 顆 |

Case 1 經 API（含分牙）：`root=virtual` 全程 145 秒（含排牙），`root=none` 116 秒（不排牙，27 顆開口牙冠、27 個牙軸）。接牙根這一步每顎：`virtual` 9–10 秒、`generated` 18–20 秒、`none` 3 秒。

**已知問題**：

- `root` 搭配 `start=generate`（用你們自己的牙冠）還沒有測過。

**怎麼試**：eztest「AI排牙」分頁的主機選「嘉義 5090 測試（牙冠用口掃）」，「牙根」選要的模式；虛擬牙根和不接牙根的結果區都有「下載牙軸（tooth_axes.json）」。API 則送 `root=virtual`、`generated` 或 `none` 到測試版網址。

## 2026-10-29　牙冠用口掃原樣、鄰牙不再干涉（測試版）

新的測試版端點 `https://ezai2.inteware.com.tw/toothssm-fit`（Service Token 同嘉義正式版）。API 和正式版完全相同，只多一個參數 `crown`，這個端點預設 `crown=exact`。正式版（嘉義、台中的 `/toothssm`）沒有改變。

**為什麼改**：原本的流程會把整顆牙（含牙冠）用 AI 重新生成，所以牙冠會偏離口掃（牙齦線附近最多約 1–3 mm），相鄰牙冠也會互相穿插。

**改了什麼**（`crown=exact`）：

- 牙冠直接用口掃原本的網格，一個點都不動；只修掉分割邊界上的鋸齒三角形。
- AI 生成的牙根只保留牙齦線以下的部分，接在牙冠邊緣下方。
- 生成的部分和鄰牙重疊時推開；兩顆口掃牙冠在緊接觸點互相壓住的薄膜切掉。
- 狀態回應多一個 `results.exact_crown`，列出每顎用上口掃牙冠的顆數、推開前後的重疊體積、切掉的接觸薄膜，以及「生成的牙佔到鄰牙位置」而被切開的牙（`engulfed`，請檢查那顆的分牙）。

**8 個測試病例的結果**（res 192，排牙前的牙齒）：

| | 原流程（`zhu`） | 新流程（`exact`） |
|---|---|---|
| 口掃牙冠的點落在結果上（≤ 0.01 mm） | 10–19% | 95–98% |
| 牙齦線附近的誤差（最差那顆的 p95） | 0.30–2.44 mm | 0.05–0.13 mm |
| 互相穿插的相鄰牙 | 每筆 10–26 對，最深 0.7–3.1 mm | 0 對（重疊體積 0） |
| 封閉 | 全部 | 全部 |
| 每筆時間 | — | 多 11–38 秒 |

**已知問題**：

- 牙冠與牙根接合帶有自我交叉的三角形。畫面上看不出來，但若矯正軟體要對單顆牙做布林運算或偏移，可能在那一帶出問題；試用時請特別留意。
- 排牙之後兩顆牙會不會再碰到，還沒有量過。

**怎麼試**：eztest「AI排牙」分頁的主機選「嘉義 5090 測試（牙冠用口掃）」；或用 API 送到上面的測試版網址。要和原流程比較，同一端點送 `crown=zhu` 即可。
